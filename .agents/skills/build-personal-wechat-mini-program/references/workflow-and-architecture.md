## 1. 输入清单

立项前收集以下事实，不清楚时从仓库、MP 后台截图或产品原型发现，不要一开始追问一长串问题：

### 主体与账号

- 普通个人、个人升级版、个体工商户、企业或其他组织；
- AppID、管理员、开发成员、体验成员；
- 认证、备案、类目和审核状态；
- 是否由服务商代注册、代开发、代运营或控制支付商户号。

### 产品与内容

- 目标用户、核心任务、首页主入口；
- 每个页面、隐藏功能、会员/付费功能、远程配置；
- 自营内容、第三方内容、UGC、AI 生成内容；
- 商品/服务/虚拟内容/广告、价格、退款、售后和投诉；
- 分享、订阅消息、客服、外部 App、公众号、其他小程序和二维码。

### 数据与技术

- 登录、头像昵称、手机号、位置、相册、摄像头、麦克风、蓝牙等；
- 数据字段、目的、存储位置、保留期、第三方处理方和删除方式；
- 后端、数据库、对象存储、域名、云环境和运维人员；
- 技术栈、构建工具、基础库、目标终端和现有测试。

使用 `assets/product-intake.yaml` 建立可复用底稿。

## 2. 功能证据矩阵

每个核心功能都填写一行 `assets/feature-category-matrix.csv`：

| 字段 | 要求 |
|---|---|
| feature_id | 稳定 ID，不使用临时页面名 |
| user_value | 用户真正完成的任务 |
| route/page | 从首页到功能的实际路径 |
| subject_route | ordinary-personal / upgraded-personal / non-personal |
| service_category | 当前后台类目全名 |
| category_scope_quote | 类目适用范围短原文与日期 |
| filing_service | 备案服务内容标识，不等于服务类目 |
| qualification | 许可证、资格、授权、备案 |
| monetization | none / ads / physical / service / virtual |
| data_permission | 字段、权限、第三方 SDK |
| review_access | 测试账号、触发步骤、特殊条件 |
| evidence | 官方 URL、后台截图、证书编号或合同 |

阻断条件：

- 任何核心功能没有类目或适用范围证据；
- 同一页面实际提供超出所选类目的隐藏服务；
- 备案服务内容与服务类目、简介和页面不一致；
- 需要的能力对当前主体/AppID 不开放；
- 资格证书与主体、有效期、经营范围不匹配。

## 3. 技术栈选择

### 尊重现有项目

先识别：

- 原生 JavaScript/TypeScript；
- Taro、uni-app、Remax、MPX 或其他跨端框架；
- npm 构建、monorepo、云开发或自建后端；
- `miniprogramRoot` 与实际产物目录。

修复或新增功能时沿用项目约定，除非现有栈已明确阻止当前官方能力、质量或维护目标。

### 绿色项目默认

优先原生 TypeScript，当以下条件成立：

- 微信是主要或唯一终端；
- 需要快速使用最新组件、基础库或开放能力；
- 个人团队希望减少框架升级与桥接问题；
- 包体和启动性能重要。

选择跨端框架，当以下条件成立：

- 同一产品必须维护 H5、支付宝、抖音、React Native 等多个端；
- 团队已有成熟组件库、测试、构建和发布流水线；
- 已接受平台特性映射、插件差异、包体、调试和升级成本。

不要仅为“技术先进”引入 Skyline、glass-easel 新特性、重状态框架或大型 UI 库。先验证目标基础库、组件兼容、真机收益和回退策略。

## 4. 后端选择

### 无后端

适合完全本地、无账号、无跨设备同步、无敏感数据、无交易和无 UGC 的工具。

仍需考虑：

- 本地存储容量与清理；
- 用户导入/导出；
- 数据丢失提示；
- 不把本地数据误称为云端备份。

### 微信云开发

适合个人开发者快速构建登录、CRUD、存储、云函数和轻量内容管理。

必须做到：

- 配置数据库和存储安全规则，不使用“所有人可读写”；
- 在云函数内校验身份、角色、资源归属、价格和状态；
- 隔离开发、测试和生产环境；
- 管理费用、配额、日志、备份和数据导出；
- 认识到云调用或支付封装不会改变主体准入。

### 自建后端/云托管

适合：

- 复杂第三方系统集成；
- 强事务、队列、搜索、数据仓库或自定义运行时；
- 受监管或高敏感数据；
- 多端共享、可迁移性和独立运维要求；
- 服务商/企业既有基础设施。

必须实现：

- API 鉴权与资源级授权；
- 参数校验、幂等、并发锁、审计日志；
- 密钥管理、最小权限、漏洞和依赖管理；
- 备份恢复、数据删除和事件响应。

## 5. 模块与数据设计

### 推荐分层

```text
pages / feature packages
  -> reusable components
  -> domain services/use-cases
  -> API/cloud adapters
  -> storage, logging, feature flags
```

避免：

- 页面直接拼接所有网络、权限、支付和数据逻辑；
- 全局单例保存大量页面状态；
- 在 WXML 中堆叠复杂表达式；
- 用远程配置改变审核时的核心业务类别；
- 把服务端鉴权放在隐藏按钮或前端角色判断中。

### 数据模型

为每个实体定义：

- 业务主键与不可预测的公开标识；
- owner/tenant/role；
- 创建、更新、删除与保留状态；
- 幂等键、版本号或并发控制字段；
- 审计字段和敏感字段分级；
- 用户注销、撤回同意和法定留存的处理。

### 状态与错误

至少设计：

- loading、empty、success、recoverable error、fatal error；
- 未登录、会话过期、无权限、资源不存在；
- 权限拒绝和稍后重试；
- 弱网、超时、重复提交、接口降级；
- 旧版本客户端与新服务端协议兼容。

## 6. 迭代顺序

按风险前置：

1. 主体、类目、资质、支付和接口可行性原型。
2. 首页到核心功能的最短闭环。
3. 登录、权限、隐私同意和服务端鉴权。
4. 数据写入、幂等、错误恢复与删除。
5. UGC 内容安全、举报和运营后台。
6. 支付/订单/退款/售后（仅可行路线）。
7. 性能、分包、弱网、兼容和自动化。
8. 备案、审核证据、灰度、更新和运营监控。

不要把类目、隐私、测试账号、内容审核或退款留到发布前一周。

## 7. 变更控制

以下变化触发一次完整门禁复审：

- 新增收费、广告、虚拟商品或交易撮合；
- 新增 UGC、评论、上传、头像昵称或 AI 生成内容；
- 新增手机号、精确位置、生物识别或敏感个人信息；
- 新增 WebView、第三方 SDK、插件或跨小程序跳转；
- 新增受监管行业内容；
- 修改名称、主体、负责人、联系方式、类目或服务范围；
- 服务商、商户号、云环境或数据处理方变化；
- 大版本迁移、基础库最低版本提高、渲染引擎切换。

每次变更同步更新功能矩阵、隐私清单、审核说明、备案判断、测试和来源证据。
