## 1. 三条主体路线

### 普通个人主体 `ordinary-personal`

适用于自助注册、非机构、非特殊服务商代开的小程序。

先记录注册渠道：`direct`（公众平台自助注册）或 `service-provider-fast-register`（第三方平台快速注册/授权）。两者都是个人主体，但认证入口、搜索/分享状态和服务商控制关系可能不同。

核心约束：

- 当前直接注册流程要求个人为 18 岁以上、具有中国大陆居民身份信息的微信实名用户；邮箱不得已用于公众平台、开放平台、企业号或绑定个人号。
- 当前公开上限为：同一身份证最多注册 5 个个人类型小程序；同一身份证、手机号、微信号分别最多绑定 5 个小程序。数量、成员和绑定规则属于高波动事实，注册当天复核。
- 当前腾讯客服提供“个人小程序微信认证申请流程”，个人可在认证中选择是否申请职业身份认证；职业身份通过后可展示在小程序资料页。
- 个人每次申请认证都需按当时协议支付审核服务费，费用不以成功为前提；个人当前仅支持电子发票。不要把历史固定价格写进预算。
- 微信开放平台另有服务商“代认证小程序”专项接口，支持个人类型；对于服务商快速注册的新账号，认证主要恢复或获得搜索、分享等展示能力，未认证不影响发布。
- 个人认证不改变个人主体。普通个人即使认证，也不能据此申请标准小程序支付、虚拟支付、`web-view`、手机号快速/实时验证或组织主体类目。
- 标准小程序支付的申请材料与主体条件仍排除普通个人；不能仅因“已认证”推导可支付。
- 服务商快速创建个人小程序页面还明确：该渠道账号不可绑定微信支付商户号。
- 虚拟支付当前要求已认证的企业、事业单位或个体工商户主体；普通个人不适用。
- `web-view` 官方组件页明确个人类型暂不支持。
- 手机号快速验证组件目前仅向已认证非个人主体开放。
- 只能提供当前“个人主体小程序开放的服务类目”覆盖的服务，且遵守每项范围中的排除条件。
- 可在满足官方公开条件时申请流量主；广告不得中断核心服务或诱导误触。

### 个人升级版 `upgraded-personal`

这是微信开放平台面向服务商的特殊能力，不等同于普通个人主体自行升级。

官方定义要点：

- 面向依法无需办理营业执照的小微商户/个人卖家，包括线上和线下场景。
- 由合格服务商代开发个人主体小程序。
- 支持交易类服务及商品类目，可绑定微信支付特约商户号并具备支付功能。
- 服务商考核结果需为“优秀”或“良好”。
- 服务商为代开发的小程序缴纳交易保证金，并协助交易争议处理。
- 具体接入指引、接口、类目和资格需由平台客服与服务商确认。

使用此路线时：

1. 验证用户是否属于依法无需营业执照的经营者，而非为了规避登记义务。
2. 验证服务商具有微信官方开放的该能力，不接受“借壳商户号”“租支付通道”等非官方替代。
3. 把代码所有权、AppID 控制权、数据控制者、商户号、结算、退款、保证金、停服迁移和服务商退出写入合同与交接清单。
4. 不推断升级版自动获得所有“已认证非个人主体”能力；手机号、WebView、直播等仍逐项实时核验。当前虚拟支付主体条件明确排除个人升级版，涉及数字内容会员、课程、PDF、AI 次数、打赏等虚拟商品时改走符合条件的组织主体，并在实施当天再核验。线下服务/实物会员应按实际权益和预付模式另行分类，不能只凭“会员”二字下结论。
5. 不使用官方 2023-07-25 的“快速创建类目参考表”作为当前升级版完整白名单。

### 必须非个人主体 `non-personal-required`

出现以下任一情况时，建议个体工商户、企业或适当组织主体：

- 业务依法应办理营业执照、许可证、前置审批或机构资质；
- 核心能力只向已认证非个人主体开放且升级版不明确支持；
- 产品需要虚拟支付、手机号、WebView、多商户平台、分账或复杂交易合规；
- 需要多员工治理、企业结算、发票、合同、长期品牌和融资；
- 个人开放类目无法覆盖全部真实服务；
- 服务商路线的控制权、成本或退出风险不可接受。

#### 从个人主体迁移到组织主体

不要假设“认证”会改变主体，也不要把“个人升级版”当作主体迁移。需要营业执照、虚拟支付、团队治理或组织资质时，单独评估小程序主体变更：

- 当前公开条件明确目标主体不能是个人，境外账号也不支持主体变更；原主体是否满足发起条件，以当前后台为准。
- 公开条件没有一概排除原个人主体，但这只能说明“可能存在迁出路径”，不能承诺当前 AppID 一定可变更。
- 变更前需处理非目标主体商户号、支付/广告服务商和广告主余额等阻塞。
- 变更后原服务类目失效，必须以目标主体资质重新申请；官方当前提示成功 7 天后代码与类目仍不一致会有 API 失效或下架风险。
- 审核费、材料、公证、插件、公众号关联和备案变化均为动态项；操作前完整读取当前主体变更条件、材料和后台提示。
- 新建组织 AppID 时 OpenID 会按 AppID 变化；仅在满足开放平台条件时评估 UnionID。设计重新登录、用户映射、历史订单/权益迁移、告知、授权和申诉，禁止用姓名/手机号等弱证据静默合并账号。
- 原 AppID 主体变更也要在体验版实测登录标识、后端会话、订阅、支付和数据权限，不能只因 AppID 看似不变就假设所有绑定不变。

### 使用快照的规则

- 将类目作为候选，不作为永久白名单。
- 按“实际核心功能”匹配，不按营销名称或页面标题匹配。
- “预约/报名”“信息查询”“办公”等宽泛类目不能覆盖一个受监管行业的底层服务。
- 一个功能若同时命中多个类目，选择所有必要类目，并保证首页可达、页面真实可用。
- 找不到匹配类目时，不建议选择最接近项试审。

## 3. 关键能力矩阵

| 能力 | 普通个人 | 个人升级版 | 说明 |
|---|---|---|---|
| 注册与开发 | 支持 | 由服务商流程创建/代开发 | 路线不同 |
| 微信认证 | 支持个人申请；可选职业身份认证；服务商场景另有代认证 | 仍是个人主体，具体入口逐服务商/AppID 核验 | 认证不等于支付、组织主体或接口准入 |
| 标准小程序支付 | 不支持标准自助路线 | 官方说明可绑定支付特约商户号 | 必须通过具备能力的服务商 |
| 虚拟支付 | 不支持 | 当前不支持 | 当前仅向已认证企业、事业单位或个体工商户开放；实施当天复核 |
| 实物/服务交易 | 普通路线不可直接标准支付 | 可在官方升级版范围内评估 | 仍受类目、资质、消费者权益约束 |
| 流量主 | 满足 500 UV、无刷粉/严重违规等条件可申请 | 逐后台核验 | 广告政策和结算信息动态 |
| `web-view` | 不支持 | 不推断支持 | 官方组件页明确个人类型暂不支持 |
| 手机号快速验证 | 不支持 | 不推断支持 | 仅认证非个人主体开放；可用其他自愿登录/联系方案 |
| `wx.login` / OpenID | 支持 | 支持性按实际 AppID 核验 | code 必须服务端换取 |
| 头像昵称填写 | 支持组件式填写 | 按实际 AppID 核验 | 使用 `chooseAvatar` 和 `input type=nickname` |
| 云开发 | 可作为后端技术方案 | 可由服务商或开发者方案使用 | 不提升主体、类目、支付资格 |
| UGC | 仅当类目和内容形态允许 | 同样需类目与治理 | 发布前检测 + 人工治理 + 投诉闭环 |
| 订阅消息/分享 | 按接口与运营规范 | 同 | 禁止强制、利诱、骚扰 |

遇到表中“不推断支持”时，检查当前 AppID 后台入口和对应 API 官方页，不能沿用普通个人或非个人结论。

## 4. 产品可行性决策树

```text
A. 是否含法律或平台禁止内容？
   是 -> PROHIBITED_OR_REDESIGN_REQUIRED

B. 列出全部真实服务、内容、商品、变现和权限
   -> 每项是否在当前普通个人类目范围内？
      否 -> 是否符合官方个人升级版且有合格服务商？
            是 -> PERSONAL_UPGRADED_ROUTE
            否 -> NON_PERSONAL_SUBJECT_REQUIRED 或删除功能

C. 是否需要机构牌照/前置审批/企业认证？
   是 -> NON_PERSONAL_SUBJECT_REQUIRED

D. 是否需要标准支付、虚拟支付、手机号或 WebView？
   标准实物/服务支付 -> 升级版或非个人主体
   虚拟支付 -> 当前必须选择符合条件的非个人主体；实施当天复核
   手机号/WebView -> 重构或非个人主体；升级版逐项核验

E. 是否能用广告而非交易变现？
   是 -> 评估流量主，但不得让广告替代实质服务

F. 名称、简介、类目、备案标识、页面是否一致？
   否 -> 先重构再开发/提审
```

## 5. 资质与备案门禁

对每项功能同时检查四层：

1. 法律层：是否需要营业执照、许可证、备案、前置审批、行业人员资格。
2. 平台主体层：个人主体是否开放该类目。
3. 平台能力层：所需 API、支付、WebView、手机号等是否对该 AppID 开放。
4. 备案层：个人主体是否可以选择对应服务内容标识，地方管局是否要求补充材料。

以下情况不得用“个人信息展示”“信息查询”“预约报名”包装：

- 医疗诊断、药品/器械、医美；
- 金融、保险、证券、借贷、征信、彩票；
- 新闻、出版、视听、直播、网络文化；
- 学历或校外培训、课程销售；
- 网约车、顺风车；
- 电商平台、多商户入驻；
- 社交婚恋、陌生人交友、公开论坛；
- 其他依法需要机构许可的经营。

## 6. 常见误判

- 把“个人主体”与“个体工商户”混为一谈。
- 把“个人已完成微信认证”误解为已经变成非个人主体，或据此承诺支付、手机号、WebView。
- 把“个人升级版”理解为普通个人后台有一个升级按钮。
- 把服务商“快速注册个人 + 代认证（搜索/分享）”与“个人升级版（交易/特约商户）”混为同一路线。
- 因云开发提供支付云调用，就认为个人主体获得支付资格。
- 因存在 `wx.requestPayment` API，就认为当前 AppID 能申请商户号。
- 因类目含“预约”，就认为可以预约任何受监管服务。
- 因类目含“信息查询”，就认为可以发布金融、医疗、新闻或政务信息。
- 因流量主可开通，就把小程序做成纯广告壳或广告解锁工具。
- 用 H5、客服消息、二维码、个人微信收款或第三方小程序绕过支付和类目限制。

## 7. 输出状态

### `PERSONAL_FEASIBLE`

全部核心功能属于当前普通个人类目，不要求特殊资质或受限能力。

### `PERSONAL_FEASIBLE_WITH_QUALIFICATION`

普通个人路线可行，但必须提供个人可合法持有的资格或完成特定条件，例如律师资格。

### `PERSONAL_UPGRADED_ROUTE`

普通个人路线因交易能力受阻，但用户符合依法无需营业执照的个人经营者条件，并可通过官方合格服务商路线继续。

### `LIVE_VERIFICATION_REQUIRED`

动态规则、地区要求或 AppID 后台能力无法当前确认。列出具体后台路径和官方页。

### `NON_PERSONAL_SUBJECT_REQUIRED`

核心业务、资质或能力必须使用个体工商户、企业或其他组织主体。

### `PROHIBITED_OR_REDESIGN_REQUIRED`

产品包含法律/平台禁止内容，或试图规避审核。不得通过换文案、隐藏入口或换类目解决。
